## Что просил пользователь (дословно по смыслу)

1. На вкладке «На компанию» показывается всего 24 варианта — должны показываться **все** подходящие
   под фильтр игры этой вкладки, и должна быть кнопка «Показать ещё».
2. В каталоге кнопка «Показать ещё» **перекидывает в самый верх страницы** — так быть не должно:
   остаёмся там, где нажали.
3. В карточках отметок иконка «не понравилось» должна быть **большим пальцем вниз**, вся линейка
   отметок — в одной стилистике.
4. На странице игры: четыре вертикальных блока и один под ними. Нижний надо **расширить на всю
   ширину четырёх** и сделать горизонтальным, **убрать из него содержимое** и **перенести туда
   содержимое блока «Особенности»**; на освободившееся место (где были «Особенности») —
   **минимальные и рекомендуемые требования к ПК**. Все блоки должны быть примерно одинаково
   заполнены, без больших пустот.
5. Почта `gustoplaysupport@gmail.com` — **основная почта сайта** для фидбека, помощи и поддержки.

## Разведка (что уже выяснено в коде)

* `js/views/party.js` — `recommendForParty({ …, limit: 24 })`, кнопки «показать ещё» нет;
  в заголовке `tp('party.result', games.length)` печатает число из выдачи (24), а строка
  «11 игр с коопом за одним экраном» считается по тем же 24 играм.
* `js/engine.js` — `recommendForParty()` уже умеет возвращать весь пул: `limit` только режет готовый
  отсортированный список в конце.
* Каталог: кнопка `data-action="show-more"` → `catalog.updateQuery({ page })` → `navigate(..., { replace })`
  → `gf:navigate` → `render(true)` → `window.scrollTo({ top: 0 })`. Отсюда прыжок наверх.
* Отметки (`js/views/components.js` → `markButtons`): played — `controller`, liked — `heart`,
  disliked — `minusCircle`, wishlist — `bookmark`. Иконок `thumbsUp`/`thumbsDown` в `js/icons.js` нет.
* Страница игры (`js/views/game.js`): `.game-details` — сетка `repeat(auto-fit, minmax(240px, 1fr))`
  из **пяти** карточек: «Об игре» (факты), «Режимы · Платформы», «Жанры», «Теги» (+шкалы) —
  это четыре блока в строке, пятая карточка «Игроки» (только иконки платформ) уезжает под них
  и выглядит пустой. Блок «Особенности» — `.game-feats` внутри `.game-info` шапки игры
  (`t('game.features')`, буллеты `game.feats`).
* Требований к ПК в проекте нет ни в каком виде — только тег `lowsysreq`. В песочнице нет сети
  к Steam (ответ 000), поэтому данные Steam в проекте тянет **GitHub Actions**: так уже сделаны
  обложки (`tools/resolve-steam-covers.mjs` + `.github/workflows/covers.yml`, доставка данных через
  аннотации прогона — `tools/emit-cover-data.mjs` + `tools/collect-cover-data.mjs`).
  В `js/catalog/steam-covers.js` лежит `steamId` для 401 игры — это ключи для Store API.
* Почта живёт в `SITE.email` (`js/config.js`; раньше `hello@gustoplay.ru`, теперь
  `gustoplaysupport@gmail.com`) и выводится в подвале (`js/app.js`), в политике конфиденциальности
  и на её отдельной странице, в условиях (`js/views/terms.js`).

## Прогон 6 (36256159139): 68 игр, и настоящая причина «пустых» ответов

Прогон шёл 33 минуты (16:38–17:12 UTC), завершился успешно и записал в ветку **68 игр из 401**
с настоящими требованиями. Его отчёт (`tools/sysreq-review.txt`):

* `Причины: в ответе нет pc_requirements — 258 | запрос не прошёл — 76`;
* `Как получены: повторный проход (2) — 88 | повторный проход (3) — 46`;
* `По проходам: проход 1 — 0 игр | проход 2 — 44 игр | проход 3 — 23 игр`;
* двенадцать строк `DIAG`, и они противоречили сами себе:

```
DIAG deep-rock-galactic (548430) ru[HTTP 200 success=true data=object pc_requirements=есть байт=59047 → нет]
DIAG left-4-dead-2 (550)         ru[HTTP 200 success=true data=object pc_requirements=есть байт=23223 → нет]
```

То есть требования в ответе **были** (карточка на 59 КБ), а сборщик записывал игру в «нет данных».
Проверка живого API (запросы к `store.steampowered.com` из этой сессии) объяснила обе странности:

| Проверка | Ответ магазина | Что это значило |
|---|---|---|
| `appids=548430&l=english` | `{"4207930":{"success":true,"data":{…,"steam_appid":548430,…}}}` | **ключ ответа не равен запрошенному appid** — сборщик искал `json["548430"]`, не находил и объявлял карточку пустой. Именно так терялись 12 игр с полными карточками |
| `appids=550&l=russian&cc=us` | `{"322070":{"success":true,"data":{…,"steam_appid":550,…}}}` | то же самое с явной витриной — от `cc` это не зависит |
| `appids=620&l=english&filters=pc_requirements` | `{"620":{"success":true,"data":[]}}` | **вариант с фильтром мёртв**: магазин принимает запрос, но отдаёт успешный ответ с пустым `data`. Поэтому первый проход прогона 6 собрал 0 игр из 401, потратив 802 запроса |

Что исправлено в `tools/pull-system-requirements.mjs`:

| Находка | Исправление |
|---|---|
| Карточка под чужим ключом | `readCard()`: сначала ключ appid, затем карточка с совпадающим `steam_appid`, затем единственная карточка в ответе. В отчёт пишется способ поиска (`найдено=…`), чтобы это не пряталось |
| `filters=pc_requirements` ничего не даёт | первый проход — обычная карточка без фильтра и без витрины (её дешевле отдаёт кэш), повторные проходы — с `cc`. Фильтр не используется вовсе: это проверяется тестом («ни один запрос не уходит с filters») |
| Требования строкой HTML вместо `{minimum, recommended}` | `reqLevels()` принимает обе формы: строка — это минимальные требования |
| Отчёт сваливал все причины в «нет pc_requirements» | `describeMissReason()` различает: запрос не прошёл, `success=false`, магазин отдал пустую карточку (троттлинг), в карточке нет блока, требования пришли но не разобрались |
| Локально нечем было проверить | заглушка в `tools/test-sysreq.mjs` теперь отвечает как настоящий магазин: пустой `data` по фильтру, карточка под **чужим ключом** с `steam_appid` внутри, требования строкой, `success=false`, троттлинг. **41 проверка** |

Простыми словами: данные в ответах магазина были всё это время — сборщик не находил карточку, потому
что искал её по ключу, а магазин кладёт её под другим идентификатором. Как только карточка ищется по
`steam_appid`, первый же проход собрал 247 игр (раньше — ноль), и «пустые ответы» из прогона 6
(deep-rock-galactic, left-4-dead-2, it-takes-two и другие) получили настоящие требования.

Осталось 3 игры — Half-Life, Civilization IV, Hitman: Blood Money. Отчёт объясняет их честно:
`Причины: требования пришли, но не разобрались — 3`, а `DIAG` показывает, что карточка нашлась
(`pc_requirements=объектом найдено=steam_appid в карточке`). Причина в формате: старые приложения
публикуют требования одной строкой без меток полей, а обе части — минимальные и рекомендуемые —
в одном поле `minimum`:

```
"pc_requirements":{"minimum":"Minimum:</strong> 500 mhz processor, 96mb ram, 16mb video card,
 Windows XP, Mouse, Keyboard, Internet Connection</p>Recommended:</strong> 800 mhz processor, …"}
```

Что добавлено (проверено на этом же живом тексте Half-Life, 46 проверок):

| Находка | Исправление |
|---|---|
| `Recommended:` лежит внутри `minimum` | `splitRecommended()` делит строку на два уровня, если отдельного поля `recommended` нет |
| Меток полей нет — разбор по полям даёт пусто | если ничего не разобралось, а текст есть, он кладётся в «Примечания» как есть (служебное слово `Minimum:`/`Рекомендуемые:` снимается). Мусор вроде «/» или «Windows» в данные не попадает: нужны минимум 25 символов и цифра |
| Пробел перед запятой после чистки единиц | `unifyUnits` убирает пробел перед `,` `.` `;` `:` («96 мб ОЗУ, мышь» → «96 мб, мышь») |

# Заход 3: блок «Подходит ли ваш ПК» на странице игры

> **Просьба:** «надо добавить еще один блок на вкладке с каждой игрой чтоб я мог выбрать свои
> комплектующие и мне показало подходит ли мой пк под эти требования или нет».
>
> Правило то же: никаких заглушек и выдуманных данных. Если сравнить нельзя — блок прямо говорит,
> что именно не проверено, и почему (модели нет в справочнике, магазин не публикует параметр).

## Что важно понять до кода (и что из этого следует)

Требования Steam — свободный текст: «Intel Core i5-2500 or AMD FX-6100», «NVIDIA GeForce GTX 660»,
«8 GB RAM», «30 GB available space», «Windows 10 64-bit». Значит, сравнивать можно не «в лоб»,
а по-разному для разных параметров:

| Параметр | Как сравниваем | Насколько это надёжно |
|---|---|---|
| Память | число из текста (GB/MB/ГБ/МБ) → гигабайты | точно |
| Место на диске | число из текста → гигабайты | точно |
| DirectX | версия из текста («11», «9.0c») против версии, которую даёт система | приблизительно: считаем по версии Windows, поддержку на стороне видеокарты не проверяем — так и написано в блоке |
| Система и разрядность | ряд версий (XP → Vista → 7 → 8 → 8.1 → 10 → 11), флаг «нужна 64-битная» | точно |
| Процессор, видеокарта | **условная таблица производительности**: и требование, и выбор пользователя ищутся в одном справочнике, сравниваются баллы | приблизительно: баллы нужны только для «больше/меньше» внутри одной таблицы. Если модели нет в справочнике — пункт честно «не проверено», а не «подходит» |

В строке может быть несколько альтернатив («GTX 660 или RX 460»): для минимальных требований
достаточно **любой** из них, поэтому порог = самая слабая распознанная альтернатива.

# Коммерческая готовность — заход 2: hardening безопасности (27.09.2026)

## Изменения

- **Google Sign-In.** Проверка ID-токена дополнена обязательным `email_verified === true`, форматом адреса, RS256/JWKS, `aud`, `azp`, временными claims, `sub`, размером токена и нормальной обработкой повреждённого JWT. Неподтверждённый адрес отклоняется до создания или привязки аккаунта.
- **Размер тела.** В Worker больше нет неограниченного `request.json()` для JSON API: auth ограничен 16 КиБ, профиль — 256 КиБ в UTF-8 + 4 КиБ оболочки, ошибка формата даёт 400, превышение — 413. Добавлены malformed/oversized и Unicode-регрессии.
- **Rate limit.** Проверка/инкремент заменены на атомарный SQLite `UPSERT … RETURNING`; e-mail в login/reset bucket больше не хранится открытым текстом, а превращается в детерминированный SHA-256 (неанонимизированный хэш, это не криптографическая приватность). Окно фиксированное, не sliding.
- **Bearer/CORS.** Клиент перестал отправлять cookies (`credentials: omit`); API не объявляет `Access-Control-Allow-Credentials`.
- **XSS.** В ходе проверки шаблонов добавлены escaping для динамических catalog-атрибутов и SVG года, HTTPS-only URL магазинов и безопасная сериализация JSON-LD, чтобы `</script>` из строки контента не завершил script в prerender.
- **Зависимости.** Уязвимый пакет `css` удалён; проверки CSS и сборка перенесены на PostCSS + esbuild. Текущий `npm audit` — 0 vulnerabilities.
- **Контакт безопасности.** `npm run build` генерирует `.well-known/security.txt` с существующим адресом поддержки, языками, canonical и сроком действия; `verify:build` проверяет формат.
- Старые неподтверждённые оценки стоимости/квот Cloudflare и почтового сервиса удалены из security-документации. Новая версия документа разделяет локальные факты и live-настройки, которых у репозитория нет.
